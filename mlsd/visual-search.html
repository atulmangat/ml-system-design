Chapter 2

Visual Search System

A user taps an image, or drags a box around part of one, and the product returns other images that look and feel similar: the same sneaker in a studio shot, a sofa with the same silhouette, a kitchen with the same mood. Pinterest Lens and Google Lens are the reference products. The hard parts are meaning (what counts as "similar" when only pixels are available) and scale (100 billion images, answered in a fraction of a second). The core idea is to learn an encoder that turns every image into a short vector, so that similar images sit close together, and then find the nearest vectors with approximate search.

Clarifying Requirements

Visual search sounds simple, so the interview is mostly about pinning down what "similar" means, how big the catalog is, and which signals exist. A candidate may open with the questions below; each answer removes a branch of the design space.

Candidate

Is the query always an image, or can users also type words to refine it?

Interviewer

Images only. Text-to-image search is a different product with its own chapter.

Candidate

Can the user select a region of the photo, and are the results images only or videos too?

Interviewer

Crops must work. Results are still images only.

Candidate

What does "similar" mean for the business: the same object, the same style, or the same topic?

Interviewer

Mostly visual and semantic similarity. A crop of a sneaker should return sneakers that look like it first, then the same style of shoe, not every picture of a foot.

Candidate

Should results depend on who is searching?

Interviewer

No personalization. The same query image returns the same results for everyone.

Candidate

May we use tags, captions, or the page an image came from?

Interviewer

Assume pixels only at query time. Metadata can exist offline, but the system must not need it.

Candidate

How large is the catalog, how fast does it grow, and what latency do we need?

Interviewer

About 100 billion images, growing by roughly 50 million per day. Results should feel instant: aim for a server-side p99 near 100 ms and well under 300 ms end to end.

Candidate

What feedback do we log that could become training labels?

Interviewer

Impressions, clicks, and saves on search results, with the query image and crop box.

Candidate

Do new images need to be searchable immediately, and how do we handle unsafe or duplicate images?

Interviewer

New images should appear within a few hours. Unsafe images must never be returned, and the first page should not be full of near-duplicates. You can assume an existing moderation classifier.

Candidate

Any constraints on hardware or on how the query photo may be used?

Interviewer

A shared GPU and CPU fleet. Treat user query photos as private: do not keep them or train on them without consent.

Build an image-to-image search system over a catalog of about 100 billion images. The input is one query image or a user-selected crop, and the output is a ranked list of visually and semantically similar images. There is no personalization and no metadata at query time, results must come back within roughly 100 ms server-side, and unsafe or near-duplicate results must be filtered.

Frame the Problem as an ML Task

ML objective

The business goal is that a user finds an image they were hoping to find. The ML translation is: given a query image, retrieve the catalog images that are most visually and semantically similar, and order them so that the most similar come first. A candidate may consider four ways to turn that sentence into a trainable objective.

Candidate objectives for "return similar images"
ObjectiveIdeaProsCons
Predict tags, match on tagsClassify each image into thousands of labels; return images that share labels with the querySimple, interpretable, reuses a classifierToo coarse: two shoes with very different shape share the tag "shoe"; the label set can never cover every visual concept
Near-duplicate hashingHash pixels so copies and light edits collideVery cheap, great for dedupeCannot find "same kind of thing"; fails on a different photo of the same item
Learn an embedding where distance means similarityTrain an encoder so that similar images map to nearby vectors and dissimilar images to distant vectorsCaptures meaning, generalizes to images never seen in training, plugs into standard nearest neighbor searchNeeds pairs or a contrastive recipe; "similar" must be defined by the training data
Learn to rank with clicksTrain a model that scores (query, candidate) pairs directly from engagementOptimizes the product metricCannot score 100 billion candidates per query; clicks are biased and sparse for new images

Decision: learn an embedding function so that cosine similarity between two embeddings approximates how similar the images look and feel. Retrieval then becomes nearest neighbor search, and any extra scoring is a cheap re-ranking step on a few hundred candidates. This is the same two-stage pattern used by Pinterest and Bing visual search.

Input and output

The input is a pixel tensor: either a whole image or a crop. The output is an ordered list of catalog image IDs, each with a similarity score. Everything else (thumbnails, links, safety status) is attached after retrieval.

ML category

This is representation learning followed by nearest neighbor retrieval. The model does not predict anything about a single image; it produces a vector, and the system compares vectors. Several model families could produce that vector.

Model families for producing image vectors

Hand-crafted features (SIFT, color histograms)Describe local gradients or color statistics, pool into a vectorNo training, cheapNo semantics: two red objects of different type look identical

Feature engineering

With pixels as the only input, feature engineering is preprocessing. The goal is that the exact same transformation runs in training, in batch embedding of the catalog, and in the online query path. A mismatch between these three is one of the most common causes of a silent quality drop.

Features by entity and how they are encoded

Crop handling deserves explicit discussion. A user crop is a small object cut out of a larger scene, and the catalog image that matches may show that object at a different scale in a different scene. Two choices follow. First, training uses random resized crops with a wide scale range (about 0.2 to 1.0 of the image area) so the encoder learns that a crop and its parent image are positives and that small objects still carry identity. Second, the product can use a quality gate: a crop of fewer than about 64 pixels is mostly interpolation noise, so the client should ask the user to select a bigger region instead of silently returning poor results.

Labels

There is no ground truth that says two images are similar. Three sources can create positive pairs, and each has a different noise profile.

Where positive pairs can come from
SourceHow it worksScaleNoise and bias
Self-supervised augmentationTwo random views of one image are a positive pair; other images in the batch are negativesUnlimited, covers the full catalogLabels are exact but narrow: it learns "same image", not "same style" or "same category"
Engagement signalsA saved or clicked result for a query becomes a positive; sessions where two images are saved together also helpBillions of pairs per monthPosition bias, popularity bias, accidental clicks, and a feedback loop with the current model
Human judgments or taxonomy labelsRaters grade pairs, or images share a curated category or productThousands to millionsAccurate but expensive, slow to refresh, and limited to the categories raters cover

Decision: combine all three, in stages. Self-supervised pairs pretrain the encoder on the whole catalog, filtered engagement pairs fine-tune what "similar" means to users, and human judgments are used mainly for evaluation, plus a small amount of high-quality fine-tuning. This mirrors the published Pinterest approach of mixing engagement and human-labeled data.

Handling the usual problems:

  • Imbalance. Head categories (fashion, food, home decor) dominate. Sample pairs with category-balanced weights, or cap the number of pairs per anchor image.
  • Noise. Keep only strong actions (saves, long dwell, clicks on the first three positions or clicks that are not immediately reversed), and drop pairs whose current-model similarity is extremely low.
  • Delay. Engagement arrives hours later, so training reads a snapshot that is at least one day old. This is acceptable because visual similarity changes slowly.
  • Bias. Higher positions get more clicks regardless of relevance. Weight clicks by inverse position propensity, or mix in random-position exploration traffic to estimate it. Without this, the model learns to reproduce its own ranking.
  • False negatives. In-batch negatives sometimes show the same item or a near-duplicate. Deduplicate the catalog by hash before sampling batches.

Model Development

Model selection

The encoder needs to be accurate and also cheap enough to run on every query and every uploaded image. The architectural choice is mostly between a convolutional network and a vision transformer.

Backbone options (parameter and compute figures are for 224x224 inputs)
BackboneSizeCompute per imageProsCons
ResNet-50about 26M paramsabout 4 GFLOPsFast, mature, strong pretrained weights, easy to quantizeLower ceiling than large transformers on semantic similarity
ViT-S/16about 22M paramsabout 4.6 GFLOPsSimilar cost to ResNet-50, strong with self-supervised pretrainingNeeds more data or good pretraining
ViT-B/16about 86M paramsabout 17.5 GFLOPsBest accuracy among these when data is plentifulRoughly 4x the serving cost of ResNet-50; re-embedding 100B images becomes expensive

Decision: start from a pretrained ResNet-50 or ViT-S as the backbone, add a linear embedding head of 128 dimensions with L2 normalization, and make the model size a budget decision rather than a quality race. Every extra GFLOP is paid once per query and once per catalog image on every model upgrade.

Do not train from scratch. A backbone pretrained on a large public image corpus already knows edges, textures, and objects; fine-tuning with the catalog and engagement pairs adapts it to the product. Fine-tuning needs far fewer steps and less data than training from scratch, and the pretrained weights are a safe baseline if the new recipe underperforms.

Embedding dimension

The embedding dimension trades quality against storage, memory bandwidth, and search time. Distance cost is linear in the dimension, and index size is the number of images times the bytes per vector.

Training data construction and loss

Each training example is built from an anchor image, one positive, and many negatives. In self-supervised mode the positive is a second random view of the same image. In fine-tuning mode the positive is an engagement or curated partner. Negatives are the other images in the batch, plus mined hard negatives.

The loss is InfoNCE, a softmax cross-entropy over similarities. For an anchor z, one positive z+, and negatives z-, in words: take the similarity to the positive divided by the temperature, take the same for every candidate (positive and negatives), and train so that the positive gets as large a share of the softmax as possible. The loss for one anchor is minus the log of that share.

If you stack the batch of anchor views against the batch of positive views, you get a square similarity matrix. Training pushes the diagonal (true pairs) up and everything else down. The off-diagonal cell between images 2 and 3 below is the hard case: two different but similar-looking items.

Worked example of the temperature. One anchor has a positive similarity of 0.80, a hard negative at 0.70 and an easy negative at 0.10. With temperature 1.0 the logits are 0.8, 0.7, 0.1, so exp gives 2.2255, 2.0138, 1.1052 (sum 5.3445); the positive's share is 0.416 and the loss is -ln(0.416) = 0.876. With temperature 0.1 the logits are 8, 7, 1, so exp gives 2980.96, 1096.63, 2.72 (sum 4080.31); the positive's share is 0.731 and the loss is 0.314. Lower temperature sharpens the softmax, so the hard negative dominates the penalty.

The gradient on each negative is proportional to its softmax probability divided by the temperature, so the share of the negative push held by the hard negative is its probability divided by the sum of all negative probabilities. The chart is that quantity for the example above: 2.0138 / (2.0138 + 1.1052) = 0.646 at temperature 1.0, and 1096.63 / (1096.63 + 2.72) = 0.998 at temperature 0.1.

A temperature that is too low is not free. The loss concentrates on the single nearest negative, and when that negative is really a near-duplicate labeled as a negative (a false negative), the model is pushed to separate images that humans would call the same. Typical values lie between 0.05 and 0.2; tune on the golden set and treat temperature as a hyperparameter that interacts with batch size and with how clean the negatives are.

Negatives: in-batch, memory queue, hard

The number and quality of negatives control embedding quality, so the candidate should compare three sources.

  • In-batch negatives. Every other image in the batch is a negative, for free. Quality improves with batch size (SimCLR uses thousands), but memory limits it.
  • Memory queue. MoCo keeps a queue of embeddings from earlier batches produced by a slowly updated momentum encoder, decoupling the number of negatives from the batch size.
  • Hard negatives. Images that the current model places near the anchor but that are not positives. After a first model exists, mine them by searching the index with training anchors and taking ranks 20 to 200, skipping the closest ones to reduce false negatives. Distance-weighted sampling works better than always taking the single hardest example, which tends to destabilize training.

Hard negatives are where most of the quality gain comes from after the first working model, and also where most of the training instability comes from. Say both. A defensible plan is: warm up with in-batch negatives only, add mined hard negatives in a later epoch, and watch the golden-set metric after each change.

Training pipeline

Two operational points. First, every stage logs the embedding dimension, preprocessing version, and temperature, because the index and the query encoder must be built from exactly the same model version. Second, retraining is a heavy event for this system: a new model means re-embedding 100 billion images, so releases are batched and gated rather than daily.

Building the evaluation set

An evaluation set for visual search cannot be a random sample of image pairs, because almost every random pair is irrelevant. Build it from queries and a pooled set of candidates.

  • Query sampling. Stratify by category, by whole image versus crop, by source (camera photo, web image, screenshot), and by popularity. Include an explicit slice of hard queries: small crops, cluttered scenes, low light.
  • Candidate pooling. Run the new model, the old model, and a simple baseline; take the union of each top 50. Judging only the new model's results would reward models that resemble the system that picked the candidates.
  • Grades. Define 0 (unrelated), 1 (same category), 2 (same style or very similar), 3 (same item or near-identical). Use three raters, adjudicate disagreements, and measure inter-rater agreement.
  • Size. About 5,000 queries with about 100 judged candidates each is enough to detect an nDCG change of roughly one point with narrow confidence intervals, and it can be refreshed quarterly. Keep the set frozen between comparisons.

The golden set can leak. If training pairs include the same images (or near-duplicates) as the evaluation queries, offline numbers look better than reality. Deduplicate the training pairs against the golden set by perceptual hash before every training run.

A/B pitfalls specific to this system: an embedding change is not a drop-in swap, because the new query encoder only works with an index built by the new model. A treatment arm therefore needs its own index (about 2.4 TB of RAM per replica in this design), which makes experiments costly and argues for fewer, larger model changes. Also segment results: a model can win on whole images and lose on small crops, and an overall average hides that. Watch for novelty effects in the first days, check for sample ratio mismatch, and run at least a full weekly cycle to cover usage patterns.

Serving

Architecture

The system has two paths. The online path embeds the query and searches the index. The offline path embeds new images and keeps the index fresh. They meet at the embedding index, and they must always use the same model version.

Component roles in one line each. Embedding service: decodes, preprocesses, and batches queries onto GPUs; if the query is a whole catalog image the stored vector is fetched instead and the GPU is skipped. ANN service: fans out to shards and merges. Re-ranking service: fetches full-precision vectors and metadata for the candidates, rescored exactly, then removes duplicates and policy violations. Indexing service: builds and publishes shards. Embedding index: compressed vectors in RAM; a separate store of float16 vectors and metadata on SSD backs re-ranking.

Memory math and compression

Storing 100 billion float32 vectors would take 51.2 TB (100 billion x 512 B) in RAM per replica, which is not realistic. Compression is therefore a requirement. Product quantization (PQ) splits each vector into m sub-vectors and replaces each with the index of its nearest centroid in a small learned codebook, usually 256 centroids per sub-vector, so each sub-vector costs 1 byte.

PQ is lossy, so distances computed from codes are approximate. The standard remedy is a two-step search: use PQ codes to find a few hundred candidates, then rescore them with the original vectors. The Pinterest unified-embedding work also reports that binarized embeddings keep precision and recall, which is another route to the same memory saving.

Numbers for one shard of 1 billion vectors, as design assumptions: 131,072 inverted lists give about 7,600 vectors per list on average; probing 32 lists scans roughly 244,000 codes, or about 3.9 MB of memory at 16 bytes per code, which a core can do in a few milliseconds using a lookup table built once per query. The recall that results depends on how many lists are probed.

Sharding and fan-out

The index is split into 100 shards of about 1 billion vectors. Random (hash-based) sharding keeps load even and makes every shard statistically alike, at the cost of every query going to every shard. The ANN coordinator sends the query vector, each shard returns its local top 50 with approximate distances, and the coordinator merges them.

  • Tail latency. A query is as slow as its slowest shard. Send a hedged duplicate to another replica after the p95 latency, and set a hard deadline (for example 40 ms) after which the coordinator merges whatever it has.
  • Partial results. Losing 1 shard of 100 loses about 1 percent of the catalog for that query, which users will not notice, so returning partial results is better than failing the request.
  • Cluster-aware sharding. An alternative is to shard by the coarse centroid so that a query visits only a few shards. It reduces fan-out cost but creates hot shards for popular topics and complicates rebalancing, so start with random sharding and revisit if compute is the bottleneck.
  • Adaptive probing. Under load, reduce the number of probed lists; the recall curve is gentle near the chosen operating point, so a small cut saves a lot of CPU.

A common follow-up is "where does personalization go?" The answer for this problem is nowhere: the requirement is that the same query gives the same results. If it were added later, it would be another re-ranking feature on the 500 candidates, not a change to the embedding.

Freshness and model upgrades

Two different lifecycles need to be handled. For freshness, the main index is rebuilt in batch (for example weekly) because training centroids and codebooks is expensive. New uploads are embedded within minutes and inserted into a small delta tier (an HNSW or flat index over the last few days of images). Each query searches both tiers and merges. At 580 new images per second, the delta tier holds about 50 million vectors per day, so it fits in RAM across a few nodes for the multi-day period before it is merged into the main index.

For model upgrades, the embedding space itself changes, so old vectors and new query vectors are not comparable. The only safe approach is a new index built by the new model, and cut over with a blue/green switch.

Re-embedding cost. At an assumed 2,000 thumbnails per second per GPU, 100 billion images need 100e9 / 2,000 = 5e7 GPU-seconds, about 13,900 GPU-hours. A pool of 1,000 GPUs finishes in roughly 14 hours, if decoding and I/O keep up (reading 1.5 PB of thumbnails in 14 hours is about 30 GB/s of aggregate throughput). A ViT-B encoder, at roughly 4x the compute, would make the same job about 56 hours on 1,000 GPUs, which is why the backbone choice is also a budget choice.

While v2 builds, v1 must keep serving and keep ingesting new uploads, so new images are embedded twice during the transition. Alternatives to a full rebuild exist: backward-compatible training constrains the new model so that new queries can search old vectors, and a learned adapter can map new queries into the old space. Both trade some quality for avoiding the backfill and are worth naming.

Failure modes and monitoring

  • Slow or dead shard. Hedged requests, deadlines, and partial results as above; alert on shard error rate and skew.
  • Encoder GPU outage. Whole-image queries can use stored vectors; crops queue briefly, then return a clear error rather than stale results.
  • Re-ranking dependency down. Skip optional signals such as diversity, but never skip the safety flag: fail closed.
  • Version mismatch. A query vector from model v2 against an index built by v1 returns plausible but wrong results with no error. The router pins both versions together, and a version tag is carried in every request and checked at the shard.

Other Talking Points

  • Object-aware indexing: run a detector at upload time and add one embedding per detected object, so a small crop of a handbag matches the handbag, not the whole outfit photo. It multiplies index size by the number of regions, which is why it is usually limited to categories like shopping.
  • Binary or heavily quantized embeddings: Pinterest reports that binarized embeddings keep precision and recall, which cuts storage and speeds Hamming-distance search, a useful lever when RAM is the bottleneck.
  • Multi-task embeddings: one embedding trained for several surfaces (related content, shopping, search) removes the cost of keeping several indexes and benefits from the pooled data.
  • Version every embedding with the model hash and preprocessing version, and refuse to compare vectors across versions; this one invariant prevents the worst silent failure in the system.
  • Distill a smaller query encoder from the large model for on-device or low-latency use, but only if it is trained to live in the same space as the indexed vectors.
  • Text and image together: a CLIP-style model lets users refine a visual query with words ("same, but in blue"), which is a natural extension but changes the evaluation and the index.
  • Explicit negative feedback ("not relevant") is a cleaner signal than clicks and can be used to mine hard negatives directly.
  • Test-time augmentation (embedding two or three views of the crop and averaging) improves robustness for tiny crops at several times the encoder cost; make it conditional on a low quality gate score.
  • Use a GPU-based index for the hottest shards or for the delta tier when QPS is high, trading cost for latency.
  • Active learning for labels: send the golden-set slices where the model is least certain or where online and offline metrics disagree to raters first, which spends rater budget where it changes decisions.

Check yourself

Questions are tagged by the level they target. The first set checks Senior-level fundamentals and arithmetic; Staff and Principal questions probe trade-offs, operations, experimentation and organization. Try to answer aloud for two minutes before opening one.

1. Why is training a tag classifier and matching on tags not enough for visual search?Tags only encode the distinctions the label set defines, so two very different shoes share the tag "shoe", and no label set covers every visual concept or style. A classifier's penultimate features discard information the labels did not need. Contrastive embedding learning optimizes distance directly, generalizes to unseen images, and its output plugs into nearest neighbor search. Tags and hashes are still useful as signals for filtering and deduplication.
2. Memory alone needs about 12 nodes per replica, yet the design runs about 400 nodes. Explain the gap.With 24 bytes per vector (16 B PQ code plus 8 B id), 100 billion vectors take 2.4 TB, which fits in about 12 nodes with 200 GB usable RAM. The fleet size is set by compute: with 100 shards every query becomes 100 shard queries, so 20,000 QPS gives 2 million shard queries per second. At about 7,100 shard queries per second per node that is 282 nodes at full load, and about 400 at a 70 percent utilization target. Fewer shards would reduce fan-out cost but increase per-shard latency; cluster-aware routing would reduce it further at the price of hot shards.
3. A relevance list for a query is [2, 3, 0] at ranks 1 to 3. Compute nDCG@3.DCG = 2/log2(2) + 3/log2(3) + 0/log2(4) = 2 + 1.893 + 0 = 3.893. The ideal order is [3, 2, 0], so IDCG = 3/1 + 2/1.585 + 0 = 3 + 1.262 = 4.262. nDCG@3 = 3.893 / 4.262 = 0.913. The 0.087 loss is entirely due to swapping the grade-3 and grade-2 results.
4. What happens if you set the contrastive temperature too low, and how do you detect it?The softmax becomes very sharp, so nearly all of the gradient lands on the single closest negative. If that negative is a false negative (a near-duplicate or the same item), the model is pushed to separate images that users consider the same, and training becomes unstable or the embedding fragments clusters. Symptoms: training loss is noisy, golden-set recall for near-duplicate pairs falls while precision at the top rises, and the nearest-neighbor distance distribution becomes bimodal. Fixes: raise the temperature, deduplicate and filter negatives, or sample hard negatives by distance weighting instead of always taking the nearest.
5. Users complain that a crop of a handbag returns photos of whole outfits. How do you diagnose and fix it?First check the slice: golden-set nDCG for small crops versus whole images, and the distribution of crop areas at query time. Likely causes: the catalog vectors describe the whole image, so the handbag is a small part of the signal; training views did not include small crops as positives of the parent; the quality gate lets through tiny crops. Fixes in order of cost: widen the random-resized-crop range and add crop-to-parent pairs; add a margin and a minimum crop size at the client; add object-level embeddings for the shopping category with a detector at upload time; add crop-size slices to the evaluation and the online guardrails.
6. The team wants to ship a better encoder next week. What must happen before the first query is served by it?The new encoder produces vectors in a different space, so the entire catalog must be re-embedded and a new index built, which is about 13,900 GPU-hours for 100 billion images at 2,000 images per second per GPU (assumption), plus a new set of centroids and PQ codebooks. Run it in shadow, check ANN recall against exact search and golden-set metrics, check latency and cost, run an A/B with its own index, then flip the router so the encoder and index change together, keeping the old index for a rollback window. If a week is not enough time, use a backward-compatible training approach or an adapter, accepting some quality loss.
Serving cost is 40 percent over budget but quality must not drop. Where do you cut, and in what order?

Start from a cost breakdown, because the chapter's math shows that fan-out compute, not raw memory, sets the fleet size. Rank levers by saved dollars per point of recall lost: (1) remove near-duplicate images before indexing, which shrinks N for free; (2) tighten the probe budget (fewer lists visited per query) by routing queries to a subset of shards through a coarse quantizer instead of broadcasting to all; (3) move the cold tail to SSD-backed or disk-based indexes while keeping the hot head in memory; (4) lower the re-ranking depth; (5) cache embeddings and results for head queries; (6) distill the query-side encoder.

For each lever, measure the recall@k loss against brute-force ground truth on a held-out query set and plot recall against cost per query. Pick the knee of that frontier, then confirm in an A/B test with guardrails on engagement and null-result rate. Do not quantize further just because it is cheap; make the recall-versus-dollar trade explicit.

Likely follow-ups: How do you build the ground truth for recall@k at this scale? · What if the cheapest lever hurts only tail queries?

What makes this Staff-level: You frame the answer as a Pareto frontier with measurements, and you separate offline recall loss from user-visible loss.

The new encoder is clearly better offline, but re-embedding 100 billion images takes weeks. How do you migrate without downtime or a quality dip?

Embeddings from different models live in different spaces, so you cannot mix them in one index. Two clean options. Option A, backward-compatible training: train the new encoder with an extra loss that aligns it to the old classifier or old embedding space, so new query vectors can search the old index immediately, and new images are embedded with the new model (the idea in backward-compatible representation learning, Shen et al., CVPR 2020). Option B, a shadow index: build the v2 index in the background, backfill in popularity order, replay live traffic against it in shadow, compare metrics, then cut over by market or by traffic percentage, keeping v1 for rollback for a couple of weeks.

Budget it: compute for 100 billion forward passes, storage for two indexes during the overlap, and the engineering cost of dual-writing new uploads to both versions. Version every vector with a model hash so a bug can never compare across spaces.

Likely follow-ups: Which option would you pick if the new model changes the embedding dimension? · How do you handle images uploaded during the backfill?

What makes this Staff-level: You see that the real constraint is the index, not the model, and you present a cutover plan with rollback and cost.

A user's crop of a face in a public photo returns visually similar photos of strangers. What are the product and ML risks, and what do you change?

The system can act as an identity-matching tool. Mitigations: exclude face-dominant crops from retrieval or return only non-face matches for them; do not train embeddings with identity labels; apply a safety classifier at index time (explicit content, minors) and filter at query time; and honor deletions by propagating tombstones to every shard, replica and cache within a defined time (for example hours, not days).

Measure it: an audit set of face-dominant queries with a human check on the results, the rate of unsafe results per million queries, and the deletion-propagation latency at the 99th percentile. Put these on the launch checklist as gates, and keep a red-team process that tries abusive queries before every encoder upgrade.

Likely follow-ups: How do you prove a deleted image is gone from every cache? · Who signs off on shipping an encoder that is better on metrics but worse on the audit?

What makes this Staff-level: You treat privacy as a design constraint with metrics and propagation SLAs, not a policy paragraph.

One embedding now serves shopping, related-pins and search. How do you govern quality when each surface wants a different trade-off?

Run the embedding as a platform product with a contract: a versioned API, a compatibility policy (no breaking vector-space changes without a migration window), and per-surface golden sets. A release gate says no surface may regress more than a stated threshold on its own golden set unless its owner signs a waiver. Surfaces keep their own re-rankers and filters so they can tune locally without retraining the shared encoder.

Decide when to fork: if joint training lifts every surface by less than the cost of the coupling (blocked launches, compromised objectives), split into a shared backbone with surface-specific heads or adapters. Measure it with an ablation (joint versus separate) and review it each half-year. The outcome you want is fewer parallel stacks without a platform team that becomes a bottleneck.

Likely follow-ups: How do you price the platform team's work to the surfaces? · What would make you split the encoder in two?

What makes this Principal-level: You reason about ownership, contracts and the cost of coupling, and you give a data-driven rule for revisiting the decision.
